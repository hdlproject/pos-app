# Ingredient Stock Batching & Review Flow — Design

**Date**: 2026-08-16
**Status**: Approved (design), pending implementation plan

## Overview

Rebuild admin ingredient management (`/admin/ingredients`) so stock changes are never applied immediately. Instead: staging a change (individually or as part of a multi-ingredient batch — the same mechanism either way) adds it to the one currently-pending batch, persisted server-side so it survives a refresh and can be reviewed at any later time. A dedicated read-only review page shows every proposed change (old → new quantity) before a single "Confirm" applies the whole batch atomically. Confirmed (and cancelled) batches are kept as a browsable accounting history — the grouped "journal entry" view the flat `StockMovement` ledger alone doesn't provide.

## Scope

**In scope:**
- New `StockAdjustmentBatch`/`StockAdjustmentLine` models + a DB-level constraint enforcing at most one `PENDING` batch at a time.
- New `stockBatch` tRPC router: `getPending`, `stageChange`, `removeLine`, `setNote`, `confirm`, `cancel`, `listHistory`.
- Fix `ingredient.create`'s frontend to expose an initial-stock field (backend already accepts `stockQty`, just never surfaced in the UI — no backend change needed here).
- Rebuilt `/admin/ingredients`: collapsible New Ingredient form (initial stock included), a pending-batch banner, per-ingredient "stage a change" popover.
- New `/admin/ingredients/review`: the read-only change report + Confirm/Cancel.
- New `/admin/ingredients/history`: browsable list of confirmed and cancelled batches, for accounting.

**Out of scope:**
- Changing `lowStockThreshold`'s meaning or the existing "LOW STOCK" badge — untouched.
- A second-person confirmation requirement (segregation of duties) — this app has one ADMIN role; the same admin can stage and confirm.
- Editing a line's delta/reason in place on the review page — removing and re-staging covers corrections, keeps the review page purely read-only plus remove/confirm/cancel actions.
- Any change to how `deductStockForOrder`/`revertStockForOrder` record `StockMovement` — those remain direct, immediate writes (a sale isn't a staged accounting decision); only ADMIN-initiated stock adjustments go through batching.

## Data Model

```prisma
enum StockBatchStatus {
  PENDING
  CONFIRMED
  CANCELLED
}

model StockAdjustmentBatch {
  id            String            @id @default(cuid())
  status        StockBatchStatus  @default(PENDING)
  note          String?
  createdAt     DateTime          @default(now())
  createdById   String
  createdBy     User              @relation("BatchCreatedBy", fields: [createdById], references: [id])
  confirmedAt   DateTime?
  confirmedById String?
  confirmedBy   User?             @relation("BatchConfirmedBy", fields: [confirmedById], references: [id])

  lines StockAdjustmentLine[]
}

model StockAdjustmentLine {
  id           String     @id @default(cuid())
  batchId      String
  batch        StockAdjustmentBatch @relation(fields: [batchId], references: [id])
  ingredientId String
  ingredient   Ingredient @relation(fields: [ingredientId], references: [id])
  delta        Decimal    @db.Decimal(10, 3)
  reason       StockReason

  @@unique([batchId, ingredientId])
}
```

`User` gains two new named relations (`createdBatches StockAdjustmentBatch[] @relation("BatchCreatedBy")`, `confirmedBatches StockAdjustmentBatch[] @relation("BatchConfirmedBy")`) alongside its existing `stockMoves`. `Ingredient` gains `adjustmentLines StockAdjustmentLine[]`.

`reason` reuses the existing `StockReason` enum (already `MANUAL_ADJUST | RESTOCK | SALE | VOID_REVERT`), but `stageChange`'s Zod input restricts the caller's choice to `MANUAL_ADJUST` / `RESTOCK` — `SALE` and `VOID_REVERT` stay exclusively system-generated by the order flow, never staged by a human.

`@@unique([batchId, ingredientId])` means re-staging the same ingredient into an already-pending batch updates that line (via upsert) instead of creating a duplicate — matches "re-staging updates the existing line."

**One pending batch at a time**: enforced two ways. Application-level, `stageChange` finds-or-creates the current `PENDING` batch rather than always creating a new one. Database-level backstop (this app's established defense-in-depth pattern), a hand-written partial unique index added to the migration SQL after Prisma's generated `CREATE TABLE` statements — Prisma's schema DSL can't express a filtered/partial unique index directly, so this line is appended by hand, the same way this project has handled enum-recreation migrations that Prisma's schema alone can't express:

```sql
CREATE UNIQUE INDEX "one_pending_stock_batch" ON "StockAdjustmentBatch" ((status)) WHERE status = 'PENDING';
```

Removing a batch's last remaining line deletes the (still-`PENDING`, never-confirmed) batch entirely rather than leaving an empty pending batch around — an empty batch has no accounting meaning and would otherwise permanently block staging a fresh one under the one-pending-batch constraint.

## Staging, Review, and Confirm

**`/admin/ingredients`**: the "New Ingredient" form (collapsible behind a button, matching the pattern already established on `/admin/menu`) gains an "Initial stock" field alongside Name/Unit/Threshold, wired to `ingredient.create`'s already-existing `stockQty` parameter.

Each ingredient row gets a "Stage Change" button opening a small popover (the `Popover` component already built for `/admin/menu`'s Filter/Sort controls): a delta number input (signed — positive for restock, negative for correction/waste) and a reason `Select` (Restock / Manual Adjust), with a "Stage" button calling `stockBatch.stageChange`.

Whenever a `PENDING` batch exists (`stockBatch.getPending`), a banner appears above the ingredient list: "N pending change(s) awaiting confirmation" with a link to `/admin/ingredients/review`. A link to `/admin/ingredients/history` sits near the page heading.

**`/admin/ingredients/review`**: reads the current pending batch via `getPending` (redirects back to `/admin/ingredients` if there isn't one). Read-only table: ingredient name, current quantity, delta, resulting quantity, reason — plus a small remove (✕) control per line calling `removeLine`. A note `Input` (`setNote`, matching the batch's optional `note` field) for the whole batch. Two actions: **Confirm** (`stockBatch.confirm`, primary/accent styled) and **Cancel** (`stockBatch.cancel`, outline styled) — both send the user back to `/admin/ingredients` on success.

**`confirm`** applies every line atomically in one transaction: for each line, increments the ingredient's `stockQty` by `delta`, creates a `StockMovement` row (`ingredientId`, `delta`, `reason` from the line, `createdById` = the confirming user), and calls `recomputeAvailabilityForIngredient` — the same three-step pattern `ingredient.adjustStock` already uses per-ingredient, just looped over every line in the batch inside one transaction. Then marks the batch `CONFIRMED`, setting `confirmedAt`/`confirmedById`.

**`cancel`** only flips the batch's `status` to `CANCELLED` — no `StockMovement` rows, no stock changes. The batch and its lines are kept (not deleted) so cancelled proposals remain visible in history, per the accounting requirement to show what was proposed even if rejected.

## Accounting History

**`/admin/ingredients/history`**: `stockBatch.listHistory` returns every batch with `status IN (CONFIRMED, CANCELLED)`, newest first, each with its lines (ingredient name, delta, reason), `createdBy`/`createdAt`, and — for confirmed ones — `confirmedBy`/`confirmedAt`. Rendered as a list of cards, one per batch: a status badge (green "Confirmed" / muted "Cancelled"), the note if present, who staged and confirmed it and when, and its line items. This is the durable, human-readable "journal entry" record — `StockMovement` itself is unchanged and still the canonical low-level ledger `report.inventoryUsage` already reads from, but batches give accounting a grouped view flat movements didn't provide.

## Testing

- `stockBatch.stageChange`: first call creates a `PENDING` batch with one line; a second call for a different ingredient adds a second line to the *same* batch (not a new one); a second call for the *same* ingredient updates that line's delta/reason rather than duplicating it.
- The one-pending-batch constraint: attempting to reach a state with two `PENDING` batches (e.g. a direct `db.stockAdjustmentBatch.create` racing `stageChange`) is rejected by the partial unique index.
- `removeLine`: removing one of several lines leaves the batch `PENDING` with the remaining lines; removing the last line deletes the batch.
- `confirm`: applies every line's delta to the correct ingredient's `stockQty`, writes one `StockMovement` per line with the right `reason`, calls the availability recompute, and marks the batch `CONFIRMED` with `confirmedById` set to the confirming user — verified end-to-end through the real mutation, not just the standalone logic.
- `cancel`: marks `CANCELLED`, and independently verifies `stockQty` on every affected ingredient is unchanged and no `StockMovement` rows were created.
- `listHistory`: returns confirmed and cancelled batches but never the pending one.
- No automated tests for the three page components themselves (presentational, matches this project's established convention) — manual end-to-end verification (stage a change, confirm it, see it in history; stage another, cancel it, see it marked cancelled in history) is the plan's closing task, following the same technique used throughout this project (real HTTP calls against a running dev server, since no browser automation is available in this environment).
